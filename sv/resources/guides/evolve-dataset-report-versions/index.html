Operativ guide · Versionsutveckling

Utveckla ett Dataset och en rapport utan att skriva om deras historik.

Använd detta flöde när Dataset-ägd SQL, source-lineage, schema, kolumner eller kolumnmetadata ändras och en befintlig rapport måste avgöra om den ska godkänna det nya kontraktet.

01

Beslutsfråga

Bevarar Dataset v3 kolumnerna, typerna, granulariteten och källinnebörden som rapporten kräver – eller ska Report v5 förbli bunden till Dataset v2 tills analyskontraktet har utformats på nytt?

02

Objekt och kontroller som används

Dataset, DatasetVersion och DatasetColumn bär det grundläggande datakontraktet. ReportVersion bär analysavsikten och exakta DatasetVersion-bindningar. AnalyticsRun registrerar en körning under aktuell styrning.

01Dataset-livscykel och oföränderlig DatasetVersion-identitet

02Normaliserad SQL, source-lineage, kolumner, typer och kända profilmetadata

03Rapportdimensioner, mått, diagram, beständiga filter och exakta bindningar

04Serverägd kompilering, behörighet, RLS och preview-kontext

03

Acceptansflöde

En ny DatasetVersion flyttar aldrig en befintlig ReportVersion av sig själv.

  1. 01

    Skapa den nya DatasetVersion

    Spara det ändrade Dataset-ägda SQL-/schema-/kolumnkontraktet och bevara samtidigt den stabila Dataset-identiteten och alla tidigare versioner.

  2. 02

    Jämför exakta versioner

    Granska normaliserad SQL-diff, source-lineage, tillagda/borttagna/ändrade kolumner, typer, nullable-tillstånd och otillgängliga historiska metadata.

  3. 03

    Utvärdera analytisk kompatibilitet

    Bekräfta avsedd granularitet, dimensioner och källfält som krävs av varje mått; härled inte kompatibilitet enbart från matchande namn.

  4. 04

    Öppna ett nytt rapportutkast

    Håll tidigare ReportVersion oföränderlig och bind utkastet till den föreslagna DatasetVersion.

  5. 05

    Validera och kompilera

    Lös metadata, validera Query Context och kompilera serverägd read-only SQL för den aktuella stödda dialektvägen.

  6. 06

    Förhandsgranska under styrning

    Kör en avgränsad preview med aktuellt behörighets- och RLS-omfång och granska diagnostik i stället för att enbart godkänna schemavalidering.

  7. 07

    Spara den godkända ReportVersion

    Bevara den nya bindningen först efter godkännande; efterföljande AnalyticsRuns pekar på exakt det paret av ReportVersion och DatasetVersion.

04

Felvägar och partiella vägar

En avvisad kandidat lämnar den tidigare produktionsinriktade rapportversionen och dess historiska körningsbindningar oförändrade.

Borttaget eller ändrat fält

Kompilering eller semantisk validering blockerar utkastet; utforma dimensionen eller måttet på nytt i stället för att ändra den gamla ReportVersion.

Preview skiljer sig oväntat

Behandla förändring av aktuella rader, källändring, filter-/RLS-omfång och kontraktsändring som separata hypoteser; en virtuell DatasetVersion är inte en snapshot av rader.

Multi-binding är partiell

Granska diagnostiken för varje bindning och bevara det partiella tillståndet; certifiera inte rapporten utifrån endast den lyckade bindningen.

05

Evidens som skapas

Versionsjämförelsen, identiteten för godkänd DatasetVersion, den oföränderliga ReportVersion-bindningen, kompilations-/konfigurations-/filter-/RLS-hashar och senare AnalyticsRun ger den registrerade kedjan för den stödda ändringen.

Report v4 → Dataset v2 · Report v5 → Dataset v2 · Report v6 → Dataset v3

06

Aktuell avgränsning

Jämförelsen omfattar registrerad SQL, schema, kolumner, metadata och lineage; den hittar inte på universell nedströms affärspåverkan. Analytics-mått, RLS och rapportbehörigheter ligger utanför det grundläggande Dataset-aggregatet, och exakta historiska rader kräver en artefakt eller ett uttryckligt kontrakt för materialiserad snapshot.

Fortsätt utforska

Relaterade perspektiv

Styrda Dataset Omvandla datadefinitioner till versionshanterade tillgångar med uttrycklig lineage.

Dataset skiljer utforskande SQL från ett återanvändbart datakontrakt. Dess stabila identitet, oföränderliga versioner och semantiska metadata skapar en kontrollerad grund för rapporter utan att dölja källans lineage.

→ Kontrollerad analys Lås datakontraktet. Styr körningen. Förklara resultatet.

Kontrollerad Analytics binder en rapport till exakta DatasetVersions, validerar Query Context på servern och bevarar behörighets-, RLS-, filter-, bindnings- och artefaktkontexten bakom ett stött resultat.

→ Operativ guide · Datalivscykel Från kända indata till ett styrt analysresultat.

Använd detta flöde när ett återkommande analysresultat måste bevara känd indata-, kvalitets-, versions-, behörighets- och körningskontext över separata kanoniska moduler.

→ advanexus Assurance Utred ett stött resultat genom den tillgängliga evidensen bakom det.

Assurance är ett behörighetsmedvetet, läsoptimerat lager för att utforska stödd operativ evidens. Det ersätter inte den kanoniska källan och skapar inte historik som aldrig registrerades.

Kort förklarat

Kan ett resultat reproduceras och förklaras senare?

advanexus bevarar exakta kontrakt och genomförandekontext där funktionen stöder det och bedömer sedan uttryckliga kriterier för reproducerbarhet. Det rapporterar reproducerbart, delvis reproducerbart, inte reproducerbart eller inte bedömt i stället för att lova universell omkörning.

Vilka bevis bevarar advanexus?

Beroende på vilken modul som stöds kan systemet koppla samman aktörer, versioner, körningar, kvalitetsbeslut, resultat, artefakter, iakttagelser, Cases och kontrollsummeverifierbara Evidence Packages. Källstyrka och saknade bevis förblir synliga; ett paket är inte automatiskt en digital signatur, en WORM-post eller en juridisk slutsats.

Framsteg som håller sambanden intakta.

advanexus förenar advance och nexus: att gå framåt utan att bryta sambandet mellan data, beslut, ansvar och evidens.
