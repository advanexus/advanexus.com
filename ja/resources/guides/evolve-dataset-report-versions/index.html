運用ガイド・バージョンの発展

履歴を書き換えずに Dataset／Report を発展させます。

Dataset 管理の SQL、ソースリネージュ、スキーマ、列、列メタデータが変更され、既存の Report が新しい契約を受け入れるか判断する必要がある場合に、このワークフローを使用します。

01

意思決定上の問い

Dataset v3 は Report が必要とする列、型、粒度、Source 意味を保持していますか。それとも分析上の契約を再設計するまで Report v5 を Dataset v2 に固定したままにすべきですか。

02

使用するオブジェクトと制御

Dataset、DatasetVersion、DatasetColumn は基盤データ契約を保持します。ReportVersion は分析上の意図／正確な DatasetVersion バインディングを保持し、AnalyticsRun は現在のガバナンス下の 1 実行を記録します。

01Dataset ライフサイクルと不変の DatasetVersion 識別情報

02正規化された SQL、Source リネージュ、列、型、既知のプロファイルメタデータ

03Report のディメンション、指標、チャート、永続的なフィルター、正確なバインディング

04サーバー管理のコンパイル、権限、RLS、プレビューコンテキスト

03

受入フロー

新しい DatasetVersion が単独で既存の ReportVersion を移動することはありません。

  1. 01

    新しい DatasetVersion を作成する

    安定した Dataset 識別情報／すべて以前のバージョンを保持しながら、変更済みの Dataset 管理の SQL/スキーマ/列契約を保存します。

  2. 02

    対象バージョンを比較する

    正規化された SQL 差分、ソースリネージュ、追加済みの/削除済みの/変更済みの列、型、NULL 許容状態、利用できない過去のメタデータを確認します。

  3. 03

    分析上の互換性を評価する

    各指標が必要とする意図された粒度、ディメンション、Source フィールドを確認します。一致する名称だけで互換性を推測しません。

  4. 04

    新しい Report 下書きを開く

    以前の ReportVersion を不変のに保ち、下書きを候補 DatasetVersion に紐付けします。

  5. 05

    検証／コンパイルする

    メタデータを解決し、Query Context を検証し、現在の対応済みの方言経路向けサーバー管理の読み取り専用の SQL をコンパイルします。

  6. 06

    ガバナンス下でプレビューする

    現在の権限／RLS スコープで制限されたプレビューを実行し、スキーマ検証だけを受け入れず診断情報を確認します。

  7. 07

    受け入れ済みの ReportVersion を保存する

    受入確認後にだけ新しいバインディングを永続化します。後続の AnalyticsRun は正確な ReportVersion／DatasetVersion 組を指します。

04

失敗および部分的な経路

拒否された候補は以前の本番向けの Report バージョン／過去の実行バインディングを変更しません。

削除／変更されたフィールド

コンパイル／セマンティックな検証が下書きをブロックします。古い ReportVersion を変更せずディメンション／指標を再設計します。

プレビューが予期せず異なる

稼働中データ行のドリフト、Source 変更、フィルター/RLS スコープ、契約変更を個別の仮説として扱います。仮想の DatasetVersion は行スナップショットではありません。

複数バインディングが部分的なになる

各バインディング診断情報を確認して部分的な状態を保持します。成功したバインディングだけで Report を認証しません。

05

生成される証拠

バージョン比較、受け入れ済みの DatasetVersion 識別情報、不変の ReportVersion バインディング、コンパイル/設定/フィルター/RLS ハッシュ、後続の AnalyticsRun が対応済みの変更の記録済みのチェーンを提供します。

Report v4 → Dataset v2 · Report v5 → Dataset v2 · Report v6 → Dataset v3

06

現在の境界

比較は記録済みの SQL、スキーマ、列、メタデータ、リネージュを対象とし、一律の下流の業務影響を捏造しません。Analytics 指標、RLS、Report 権限は基盤 Dataset 集計の外にあり、正確な過去の行には成果物または明示的なマテリアライズされたスナップショット契約が必要です。

関連する視点

ガバナンスされた Dataset データ定義を、明示的なリネージュを持つバージョン管理資産へ変換します。

Dataset は探索用の SQL と再利用可能なデータ契約を分離します。安定した識別情報、不変のバージョン、セマンティックなメタデータにより、ソースリネージュを隠さずに Report の制御された基盤を作ります。

→ 制御された Analytics データ契約を固定する。実行をガバナンスする。結果を説明する。

制御された Analytics は、Report を正確な DatasetVersion に結び付け、Query Context をサーバー上で検証し、対応済み結果の背後にある権限、RLS、フィルター、バインディング、アーティファクトのコンテキストを保持します。

→ 運用ガイド・データライフサイクル 既知の入力から、ガバナンスされた分析結果へ。

繰り返し生成する分析結果について、別々の正規モジュールを横断して既知の入力、品質、バージョン、権限、実行コンテキストを保持する必要がある場合に、このワークフローを使用します。

→ advanexus Assurance 対応済みの成果を、その背後にある利用可能な証拠から調査します。

Assurance は、対応する運用証拠を探索するための、権限認識型かつ読み取り最適化されたレイヤーです。正規ソースを置き換えることも、記録されていない履歴を作り出すこともありません。

簡潔に知る

成果を後から再現し、説明できますか？

advanexus は能力が対応する範囲で正確な契約と実行コンテキストを保持し、明示的な再現可能性基準を評価します。万能な再実行を約束せず、再現可能、部分的に再現可能、再現不可能、未評価のいずれかを報告します。

advanexus はどの証拠を保持しますか？

対応するモジュールに応じて、アクター、バージョン、実行、品質判断、成果、アーティファクト、Finding、Case、チェックサム検証可能な Evidence Package を接続できます。情報源の強度と不足する証拠は可視のままで、パッケージが自動的にデジタル署名、WORM 記録、法的結論になることはありません。

つながりを保ったまま、前へ。

advanexus は advance と nexus の融合。データ、意思決定、説明責任、証拠のつながりを切らずに前へ進むことを表します。
